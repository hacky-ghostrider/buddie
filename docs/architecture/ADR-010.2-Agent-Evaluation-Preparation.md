# ADR-010.2: Agent Evaluation Preparation

- **Status:** Accepted  
- **Date:** 2026-08-07  
- **Sprint:** 10.2 (Architecture Hardening)  
- **Supplements:** [ADR-010](ADR-010-AI-Evaluation-Automation.md)

## Context

Sprint 10 delivered DeepEval adapters, LangSmith tracing, tool validation,
golden datasets, and automation runners. Sprint 11 will add a LangGraph
agent (planner, router, tool execution). Without a hardening pass, Sprint 11
would force signature churn: more evaluate kwargs, LangSmith parsing inside
validators, and ad-hoc assertions for tool policy.

We need **evaluation architecture ready for agents** without implementing
agents, MCP, or tool calling yet.

## Decision

1. **`EvaluationContext`** (`app/evaluation/context.py`) — one aggregate DTO
   for question, retrieval, prompt, tools, answer, model, latency, tokens,
   cost, LangSmith ids, correlation id, and timestamp. Metrics keep using
   Sprint 9 fields (`question`, `answer`, `retrieved_documents`, …).
2. **`ToolContract`** — declarative expected tool behaviour (required /
   optional args, validators, order, call bounds, latency, output type).
3. **`ToolExecution`** — vendor-neutral observed tool invocation.
4. **`ToolTraceMapper`** — LangSmith-like traces → `ToolExecution` →
   `ActualToolCall`. `ToolValidator` never parses LangSmith objects.
5. **Canonical demo dataset** — `datasets/agent-tools-foundation-001.json`
   (scenario id `agent-tools-foundation-001`) remains stable across Sprint 11.

## Why EvaluationContext

Many parallel parameters create brittle APIs. One context object is the
same idea as a typed `TestContext` in Java automation: add fields once,
consumers opt in. Future frameworks (DeepEval adapters, regression, agents)
read the snapshot instead of inventing new kwargs.

## Why ToolContract

Scattered `assert tool_name == ...` checks duplicate policy and drift from
goldens. Contracts are the **spec** (like OpenAPI for tools). Validators
and datasets share one source of truth; interviews can point at a contract
instead of a pile of asserts.

## Why ToolTraceMapper

Anti-corruption layer. Vendor run trees change; assertion logic must not.
Mapper in → internal model → validator. Swap LangSmith for Phoenix /
LangGraph dumps without rewriting `ToolValidator`.

## Why Canonical Demo Dataset

Interviewers and CI need one frozen scenario that demonstrates:

| Sprint | Expected tools | Actual tools | Meaning |
|--------|----------------|--------------|---------|
| 10.2 | `search_docs`, `summarize` | `[]` | Infrastructure only |
| 11 | `search_docs`, `summarize` | `search_docs`, `summarize` | Agent executes |

The scenario id and expectations **do not change** in Sprint 11 — only
actual executions appear.

## Why these abstractions before LangGraph

Building the agent first would couple evaluation to LangGraph state shapes.
Defining contracts and mappers first inverts the dependency: Sprint 11 plugs
executions into seams that already exist (Dependency Inversion).

## Architecture

```text
Question
   ↓
Expected ToolContract
   ↓
Future LangGraph Agent (Sprint 11)
   ↓
LangSmith Trace
   ↓
ToolTraceMapper
   ↓
ToolExecution → ActualToolCall
   ↓
ToolValidator (+ DeepEval via EvaluationContext)
   ↓
Evaluation Report
```

## Consequences

- Public Sprint 9–10 APIs remain compatible (`answer`, `ActualToolCall`,
  `validate_from_golden`, …).
- Automation may attach a serialized `evaluation_context` on report metadata.
- No new runtime config flags required.
- Sprint 11 should not need further evaluation architecture refactors.

## Teaching notes (Java SDET → AI Evaluation)

| Abstraction | Closest Java testing analogue |
|-------------|-------------------------------|
| EvaluationContext | Scenario / TestContext DTO |
| ToolContract | API contract / page-object expected interactions |
| ToolExecution | Normalized HTTP/call record |
| ToolTraceMapper | WireMock / CDP response → domain event mapper |
| ToolValidator | Soft-assert suite over interaction sequence |
